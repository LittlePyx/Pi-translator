# PDF 全文翻译截图预准备

## 实现

后台全文视觉任务在当前模型请求等待期间，准备下一个已授权区域的截图；只持有一个后续截图，不预取整篇。请求顺序、原文区域、裁剪分辨率、公式校验和上下文生成方式保持一致。跨页密集段按既有子区域计划顺序消费截图。

暂停、停止、错误、完成和释放任务时清除预准备槽。已开始的本地渲染可能完成，但不会因此发送模型请求；恢复时按当前区域重新取图。预准备失败在轮到该区域时报告，不产生未处理的异步拒绝或隐藏网络重试。当前完成子区域仍沿用检查点机制。

此轮优化后台全文视觉链路；单段重试/前台回退仍使用原有串行流程。纯文字请求不启动图像预准备。尚未启用两个模型请求并发：上下文连续性与真实接口限流/质量尚未对照验证。

## 耗时记录

后台快照 `performance` 提供数值汇总，任务暂停/完成/失败时输出本地控制台 `[Pi PDF timing]`：

- `captures` / `prefetched`：消费截图数、命中预准备数。
- `pageRenderMs`：读取页面和渲染画布时间。
- `cropEncodeMs`：裁剪、拼接、编码等其余截图时间。
- `captureWaitMs`：请求前实际等待截图的时间，可用来衡量预准备减少了多少空档。
- `requestMs`：取得运行时请求响应的总等待时间，包含扩展调度、传输和服务端处理；不能据此单独声称测得服务端生成耗时。
- `validationMs`：本地视觉结果校验时间。

这些阶段存在重叠，不能直接相加当作墙钟总时长。只汇总已消费截图及返回响应，不是所有取消/未消费渲染的资源审计。日志不含正文、截图、密钥、文件地址，不上传或长期保存。现有翻译显示耗时记录继续沿用原链路。

## 本地对照

工具：`tools/pdf-capture-benchmark.ts`。用户本地 HATNet 第 4–5 页选取 8 个区域，真实 Edge 渲染和裁剪；每个模型请求用 200 毫秒本地等待模拟，没有外部请求。顺序采用串行、预准备、预准备、串行，减少预热顺序偏差。

| 模式 | 总耗时两次（毫秒） | 平均总耗时 | 平均等待截图 |
| --- | --- | --- | --- |
| 串行 | 3192.4 / 3344.0 | 3268.2 | 1609.3 |
| 提前准备一个区域 | 2274.4 / 2032.1 | 2153.3 | 447.3 |

本地模拟总耗时减少约 34.1%，等待截图减少约 72.2%。四次各区域截图字节完全相同。证据：`output/pdf/capture-speed-2026-09-07/benchmark.json`。

结果只说明此机器的本地准备可与等待重叠；真实接口耗时、网络和限流会影响最终收益，不能宣传为真实翻译固定提速 34%。未评估真实模型两路并发的翻译质量。
